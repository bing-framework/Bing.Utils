# 多模块批量迁移总控提示词（Multi-Module Batch Controller）

> 版本：v1.0（连续执行版）

使用 $test-project-boundary skill，并严格遵循 AGENTS.md。

任务：执行“多模块批量测试重归类迁移”，将 `Bing.Utils.Tests` 中明确属于多个目标模块的测试迁移到各自模块专属测试项目，并完成验证与文档更新。

## 本轮目标模块（必填）
请根据本次任务填写目标模块清单（示例）：
- `Bing.Utils.IdUtils` -> `Bing.Utils.IdUtils.Tests`
- `Bing.Utils.Text` -> `Bing.Utils.Text.Tests`
- `Bing.Utils.Collections` -> `Bing.Utils.Collections.Tests`
- `Bing.Utils.DateTime` -> `Bing.Utils.DateTime.Tests`

> 若模块较多，请允许自动拆分为子批次（如 Batch-1 / Batch-2）。

## 执行范围
- 允许修改：
  - `tests/*`
  - `docs/quality/*`
- 不允许修改：
  - `src/*`（生产代码）

## 本轮处理范围
- 仅处理 `Bing.Utils.Tests` 中与“本轮目标模块”相关的测试
- 仅处理“可直接迁移（文件级）”项
- 不处理：
  - 混合测试类（需拆分）
  - 待人工确认项
  - 与本轮目标模块无关的测试

## 必须遵循的规则
1. 先读取并简要总结以下规则与文档（不要跳过）：
   - `AGENTS.md`
   - `.agents/skills/test-project-boundary/refs/test-project-boundary.md`
   - `docs/quality/test-reclassification-plan.md`
2. 按“主要断言目标”判断归属，不按引用数量判断
3. 迁移时保持测试方法命名、断言语义、测试意图不变
4. 先输出清单，再执行修改
5. 不确定项标记 TODO，不要强行迁移

## 执行步骤（按顺序）

### 第1步：多模块审计与迁移清单（先不改代码）
扫描 `tests/*`（重点 `Bing.Utils.Tests`），按“目标测试项目”分组输出迁移清单。

对于每个目标模块/测试项目，输出：
- 可直接迁移（文件级）
- 混合测试（需拆分）
- 待人工确认项
- 应保留在 `Bing.Utils.Tests` 的相关项（如通用/跨模块）

要求：
- 给出文件路径、测试类名、分类依据（主要断言目标）
- 明确本轮“实际执行范围”仅包括可直接迁移项
- 如果总量较大，自动拆分为子批次（如 `Batch-1`, `Batch-2`），并说明拆分依据（按模块/按文件数）

### 第2步：执行本轮迁移（仅处理可直接迁移项）
根据第1步清单执行迁移，按目标模块逐个处理：

迁移要求：
- 优先使用 move/rename（保持历史友好）
- 做最小修复：
  - 命名空间
  - using
  - 测试项目引用（csproj，如需要）
  - 必要的测试辅助类依赖（仅最小处理）
- 不改变测试语义与断言意图
- 不处理混合测试与待确认项（只记录 TODO）

禁止事项：
- 不修改生产代码
- 不顺带重构整个测试目录结构
- 不将混合测试类强行整类迁移
- 不处理与本轮目标模块无关的测试

### 第3步：最小验证
对本轮迁移结果做最小验证，并输出结果：
- 每个目标测试项目的编译情况（逐模块列出）
- `Bing.Utils.Tests` 编译情况
- 本轮涉及测试项目的测试运行情况（如可执行）

若无法运行测试：
- 说明原因
- 给出替代验证（编译检查 / 结构检查 / 引用检查 / 文件比对）

同时检查：
- 是否存在重复测试残留（迁移后旧文件未清理）
- 是否存在失效 using / 引用断裂
- 是否仅修改允许范围（`tests/*` + `docs/quality/*`）

### 第4步：更新规划文档（批次状态）
更新：
`docs/quality/test-reclassification-plan.md`

要求：
1. 更新本轮涉及模块的审计结果状态（已处理/待处理）
2. 更新迁移批次规划（如拆分为 Batch-1 / Batch-2）
3. 在 `11. 执行记录` 中新增一轮记录（例如：`第 X 轮（Batch：IdUtils + Text + Collections）`）
4. 将混合测试与待确认项同步到对应章节（如有新增）

### 第5步：生成本轮迁移验证报告
生成并保存报告到（建议）：
`docs/quality/migration-reports/YYYY-MM-DD-batch-<modules>.md`

命名示例：
- `YYYY-MM-DD-batch-idutils-text-collections.md`
- `YYYY-MM-DD-batch-datetime-reflection.md`

报告内容需包含：
- 执行范围与规则摘要
- 各目标模块迁移清单（已执行 / 未执行）
- 实施变更明细
- 验证结果（按模块汇总）
- 风险与遗留事项（混合测试、待确认项、共享辅助类耦合）
- 本轮结论（成功 / 部分成功 / 失败）
- 下一步建议（继续下一子批次 / 转混合拆分专项）

如果某些验证无法执行，不要中断任务，继续完成报告，并在报告中明确记录原因与替代验证方式。

### 第6步：更新迁移报告索引
更新：
`docs/quality/migration-reports/README.md`

要求：
- 在对应阶段分组（Pilot / P0 / P1 / P2）下新增本轮记录
- 更新 `4.2 当前进度概览`（阶段状态 / 已完成轮次）
- 如适用，更新关键指标（可保留 TODO）

## 执行策略（连续运行）
- 将本次工作视为一个端到端任务，连续执行直到完成：
  多模块清单 -> 迁移 -> 最小修复 -> 验证 -> 规划文档更新 -> 报告 -> 索引更新
- 不要在每个小步骤后询问“是否继续”
- 仅在以下情况暂停并请求确认：
  1) 需要修改 `src/*`
  2) 需要工作区外写入或网络访问
  3) 出现高风险不确定归属项无法安全判定
  4) 编译/测试失败且继续会扩大影响
- 对可暂缓问题，写入 TODO 并继续后续步骤
- 如果给出“下一步建议”，默认执行建议中的第1项，不等待确认
- 如果本轮目标模块较多，自动拆分子批次并先完整完成第一个子批次（含报告与索引更新）

## 输出格式（固定）
请按以下结构输出本次任务结果：
1. 使用规则摘要（已读取哪些规则与文档）
2. 多模块审计与迁移清单（按目标测试项目分组）
3. 实施变更（按模块说明迁移文件与最小修复）
4. 验证结果（按模块编译/测试/结构检查）
5. 文档更新结果（规划文档、报告、索引）
6. 剩余 TODO / 风险 / 下一步建议（如混合测试拆分、下一子批次）

## 额外稳妥要求（可选启用）
- 如果本轮总迁移项过多，请自动限制为一个“子批次”执行（例如最多 8~15 个文件），并在报告中列出剩余项作为下一子批次输入。
- 在每个迁移文件摘要中，简要说明归属判定依据（为什么属于该模块）。
