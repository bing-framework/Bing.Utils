# 多模块混合测试拆分总控提示词（Multi-Module Mixed Split Controller）

> 版本：v1.0（连续执行版）

使用 $test-project-boundary skill，并严格遵循 AGENTS.md。

任务：执行“多模块混合测试拆分专项”，将 `Bing.Utils.Tests`（或其他通用测试项目）中涉及多个模块的混合测试类按“测试方法粒度”拆分，并将属于目标模块的测试方法迁移到对应模块专属测试项目，同时完成验证与文档更新。

## 本轮目标模块（必填）
请根据本次任务填写目标模块清单（示例）：
- `Bing.Utils.IdUtils` -> `Bing.Utils.IdUtils.Tests`
- `Bing.Utils.Text` -> `Bing.Utils.Text.Tests`
- `Bing.Utils.Collections` -> `Bing.Utils.Collections.Tests`
- `Bing.Utils.DateTime` -> `Bing.Utils.DateTime.Tests`

> 本模板仅处理“混合测试类拆分”，不处理纯可直接迁移项（除非你明确授权合并处理）。

## 执行范围
- 允许修改：
  - `tests/*`
  - `docs/quality/*`
- 不允许修改：
  - `src/*`（生产代码）

## 本轮处理范围
- 仅处理规划文档或迁移报告中已标记为“混合测试（需拆分）”且涉及本轮目标模块的测试类
- 按测试方法粒度拆分
- 不处理：
  - 纯可直接迁移项（除非明确授权）
  - 待人工确认项（只记录 TODO）
  - 与本轮目标模块无关的混合测试类

## 必须遵循的规则
1. 先读取并简要总结以下规则与文档（不要跳过）：
   - `AGENTS.md`
   - `.agents/skills/test-project-boundary/refs/test-project-boundary.md`
   - `docs/quality/test-reclassification-plan.md`
   - `docs/quality/migration-reports/README.md`（如存在历史批次）
2. 按“主要断言目标”判断测试方法归属，不按引用数量判断
3. 优先按“测试方法粒度”拆分，不默认整类复制
4. 保持测试方法名称、断言语义、测试数据意图不变
5. 先输出方法级拆分方案，再执行修改
6. 不确定归属项标记 TODO，不要强行拆分

## 执行步骤（按顺序）

### 第1步：确认本轮混合测试拆分清单（先不改代码）
基于规划文档、历史迁移报告与当前代码，确认本轮需要处理的混合测试类清单，并按测试类输出：

- 文件路径
- 测试类名
- 涉及模块（例如 `IdUtils + Text` / `Collections + DateTime + Common`）
- 当前所在测试项目
- 拆分风险（Fixture / 共享辅助方法 / 私有测试数据工厂 / 命名空间耦合）
- 是否适合本轮处理（是 / 否）

输出分类：
- 本轮可拆分（优先处理）
- 暂缓处理（风险高）
- 待人工确认

要求：
- 说明“为什么纳入本轮”（与目标模块的关联）
- 如果数量过多，自动拆分为子批次（例如 `Mixed-Batch-1`, `Mixed-Batch-2`），并说明拆分依据

### 第2步：生成方法级拆分方案（先不改代码）
对“本轮可拆分”项，逐个测试类输出方法级拆分计划。

每个测试类至少说明：
1. 拟迁移到各目标测试项目的测试方法列表（按目标模块分组）
   - 例如：
     - 迁移到 `Bing.Utils.IdUtils.Tests`：`MethodA`, `MethodC`
     - 迁移到 `Bing.Utils.Text.Tests`：`MethodB`
2. 保留在原测试项目的测试方法列表（通用 / 跨模块 / 非目标模块）
3. 需要复制或重建的最小辅助代码（私有方法、测试数据、fixture 片段）
4. 目标目录 / 目标测试类命名建议
5. 风险与 TODO（如某方法归属不确定、拆分会破坏共享上下文）

要求：
- 对每个拟迁移方法给出“归属判定依据”（主要断言目标）
- 如果一个测试类无法安全拆分，标记 TODO 并说明原因，不要强拆

### 第3步：执行混合测试拆分迁移（仅处理已确认可拆分项）
根据第2步方案执行方法级拆分迁移。

执行要求：
- 将属于目标模块的测试方法迁移到对应模块专属测试项目
- 非目标模块测试方法保留原处（或本轮不处理）
- 优先保持测试方法签名、命名与断言不变
- 允许复制“最小必要辅助代码”（短期方案），避免引入大规模测试基础设施重构
- 修复最小范围内容：
  - 命名空间
  - using
  - csproj 引用（如需要）
  - fixture / helper 依赖
- 清理因拆分导致的空类 / 无用 using（若安全可做）

禁止事项：
- 不修改生产代码
- 不顺带重构整个测试项目结构
- 不处理与本轮无关的测试类
- 不改变测试行为语义

### 第4步：最小验证
对本轮拆分迁移结果做最小验证，并输出结果：

- 各目标测试项目编译情况（逐模块列出）
- 源测试项目（如 `Bing.Utils.Tests`）编译情况
- 本轮涉及测试类的测试运行情况（如可执行）
- 若无法运行测试，说明原因并给出替代验证（编译检查 / 结构检查 / 引用检查 / 文件比对）

同时检查：
- 是否存在重复测试方法（拆分后原类未删除对应方法）
- 是否存在失效 fixture / helper 引用
- 是否存在命名空间/目录不一致问题
- 是否仅修改允许范围（`02-tests/*` + `docs/quality/*`）

### 第5步：更新规划文档（混合测试状态）
更新：
`docs/quality/test-reclassification-plan.md`

要求：
1. 更新本轮涉及模块对应章节中的“混合测试（需拆分）”状态（已拆分 / 暂缓 / 待确认）
2. 将新增待人工确认项同步到 `10. 待人工确认项`
3. 在 `11. 执行记录` 中新增一轮记录（例如：`第 X 轮（Mixed Split：IdUtils + Text）`）
4. 如拆分为子批次，记录 `Mixed-Batch-1 / 2` 进度

### 第6步：生成本轮迁移验证报告（混合拆分专项）
生成并保存报告到（建议）：
`docs/quality/migration-reports/YYYY-MM-DD-mixed-batch-<modules>.md`

命名示例：
- `YYYY-MM-DD-mixed-batch-idutils-text.md`
- `YYYY-MM-DD-mixed-batch-collections-datetime.md`

报告内容需包含：
- 本轮处理范围（混合测试拆分专项）
- 混合测试清单确认结果（可拆分 / 暂缓 / 待确认）
- 方法级拆分方案摘要（按测试类）
- 实施变更明细
- 验证结果（按模块汇总）
- 遗留风险（高耦合类、待人工确认方法、共享辅助类）
- 下一步建议（继续下一子批次 / 转普通批量迁移）

### 第7步：更新迁移报告索引
更新：
`docs/quality/migration-reports/README.md`

要求：
- 在对应阶段分组（通常 P1，或按你的规划）下新增本轮记录
- 更新 `4.2 当前进度概览`（阶段状态 / 已完成轮次）
- 如适用，更新关键指标（可保留 TODO）

## 执行策略（连续运行）
- 将本次工作视为一个端到端任务，连续执行直到完成：
  混合清单确认 -> 方法级拆分方案 -> 拆分迁移 -> 验证 -> 规划文档更新 -> 报告 -> 索引更新
- 不要在每个小步骤后询问“是否继续”
- 仅在以下情况暂停并请求确认：
  1) 需要修改 `src/*`
  2) 需要工作区外写入或网络访问
  3) 出现高风险不确定归属项无法安全判定
  4) 编译/测试失败且继续会扩大影响
- 对可暂缓问题，写入 TODO 并继续后续步骤
- 如果给出“下一步建议”，默认执行建议中的第1项，不等待确认
- 如果本轮混合测试类过多，自动拆分子批次并先完整完成第一个子批次（含报告与索引更新）

## 输出格式（固定）
请按以下结构输出本次任务结果：
1. 使用规则摘要（已读取哪些规则与文档）
2. 混合测试清单确认结果（本轮可拆分 / 暂缓 / 待确认）
3. 方法级拆分方案摘要（按测试类，按模块分组）
4. 实施变更（拆分迁移了哪些方法/类，做了哪些最小修复）
5. 验证结果（按模块编译/测试/结构检查）
6. 文档更新结果（规划文档、报告、索引）
7. 剩余 TODO / 风险 / 下一步建议

## 额外稳妥要求（可选启用）
- 如果本轮可拆分的混合测试类过多，请先处理 1~3 个代表性测试类作为拆分试点，并在报告中说明剩余项留待下一子批次。
- 对每个被拆分的测试方法，在输出摘要中简要说明“归属到某模块的判定依据”。
