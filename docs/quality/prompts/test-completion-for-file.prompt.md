# 指定文件补全单元测试总控提示词（Test Completion for File）

> 版本：v1.1（六类边界清单接入）

使用 $test-project-boundary skill，并严格遵循 AGENTS.md。

统一使用 [六类边界检查清单](../boundary-test-checklist.md)，逐项记录适用性、预期行为及证据；正常路径仍须覆盖。

任务：针对“指定源码文件”补全单元测试（增量方式），生成或完善对应测试文件；不做无关模块迁移，不修改生产代码逻辑（除非明确授权）。

## 输入参数（执行前填写）
- 源码文件（必填）：`<SOURCE_FILE_PATH>`
- 目标测试项目（必填）：`<TARGET_TEST_PROJECT_PATH>`
- 目标测试文件（可选，建议填写）：`<TARGET_TEST_FILE_PATH>`
- 测试框架：`xUnit`（如项目已有约定请沿用）
- Mock 框架：按仓库现有约定（如无必要不引入）
- 执行模式：增量补全（默认），不要重写已有测试文件

## 执行范围
- 允许修改：
  - 指定测试项目中的目标测试文件
  - 必要的测试辅助文件（仅最小范围）
  - `docs/quality/*`（仅当我明确要求记录报告时）
- 不允许修改：
  - `src/*`（生产代码）
  - 与本任务无关的测试文件

## 任务目标
围绕指定源码文件中的公开 API（以及必要的 internal API，如项目已有可测试约定）补全测试，优先覆盖：

1. 正常路径（Happy Path）
2. 边界值 / 空值 / 默认值
3. 异常路径（参数校验、非法输入）
4. 关键分支逻辑
5. 回归风险点（从源码注释 / XML 注释推断的行为约束）

> 对于纯函数/工具方法，优先使用 xUnit `[Theory] + [InlineData]` 覆盖多组输入输出，减少重复测试代码。

## 必须遵循的规则
1. 先读取并简要总结：
   - `AGENTS.md`
   - 指定源码文件
   - 目标测试文件（如果存在）
   - `docs/quality/boundary-test-checklist.md`
2. 先输出“测试补全计划”（不要直接写代码）
3. 保持测试命名清晰，表达行为与预期
4. 预期行为追溯到方案、接口/XML 契约或确认过的兼容行为；源码推断须注明依据，仍无法确认的标记“待确认”，不写猜测断言
5. 若某些方法不适合单元测试（强依赖外部资源/环境），先标记并说明原因
6. 尽量使用现有测试风格（命名、断言风格、Fixture 风格、测试类结构）

## 执行步骤（按顺序）

### 第1步：分析与差距识别（先不改代码）
输出以下内容：
- 源码文件中的可测试成员清单（按类/方法）
- 当前测试覆盖情况（若目标测试文件已存在）
- 缺失测试清单（按优先级：高/中/低）
- 风险点（边界、异常、时间、随机数、文化区域、线程安全等）
- 按统一记录模板输出 `null/empty/invalid/overflow/concurrent/perf` 六行；已有覆盖引用现有测试，不适用项写明依据，待确认项列明缺少的契约

### 第2步：测试补全计划（先不改代码）
按“测试类 -> 测试方法”输出计划，至少包含：
- 拟新增/补全的测试方法名
- 测试目的
- 输入与预期结果
- 是否使用参数化测试（`[Theory] / [InlineData]`）
- 是否需要最小辅助方法 / 测试数据构造器

要求：
- 优先补高风险/高价值测试
- 尽量避免生成重复测试
- 若已有同类测试风格，保持一致
- 只为本次成员的明确缺口补测，不扩展为全 API 扫描；并发及性能不适用时保留说明，不机械生成测试

### 第3步：执行补全（修改测试代码）
根据第2步计划执行：
- 若目标测试文件不存在：创建对应测试文件
- 若目标测试文件已存在：在原文件中增量补全（保持风格一致）
- 做最小修复：
  - `using`
  - 命名空间
  - 必要测试引用（仅在确实需要时）
- 不修改生产代码逻辑（`src/*`）

### 第4步：最小验证
输出：
- 目标测试项目编译情况（如可执行）
- 目标测试运行情况（如可执行，可按类/方法级过滤运行）
- 若无法运行测试，说明原因并提供替代验证（编译检查 / 静态检查 / 结构检查）

同时检查：
- 测试命名是否清晰且一致
- 是否存在重复/冗余测试
- 是否覆盖关键边界与异常路径
- 是否仅修改允许范围
- 是否区分本次实际执行和旧证据复用；性能负载、阈值或环境未批准时标注对应阻塞，不自动新增依赖、CI、基线或探针

### 第5步：结果总结
请按以下结构输出：
1. 已分析文件与规则摘要
2. 覆盖差距与风险点
3. 新增/补全测试清单（按类/方法）
4. 验证结果（编译/测试）
5. 未覆盖项与原因（TODO）
6. 下一步建议（如参数化扩展 / 集成测试 / 边界补强）

## 执行策略（连续运行）
- 将本次工作视为一个端到端任务，连续执行直到完成：
  分析 -> 计划 -> 补全 -> 验证 -> 总结
- 不要在每个小步骤后询问“是否继续”
- 仅在以下情况暂停并请求确认：
  1) 需要修改生产代码（`src/*`）
  2) 无法从源码/注释确定行为语义，可能写出错误断言
  3) 需要引入较大测试基础设施重构（超出本轮范围）
  4) 现有测试风格冲突明显，无法安全增量补全

## 输出格式（固定）
请按以下结构输出本次任务结果：
1. 使用规则摘要（已读取哪些文件/规则）
2. 分析与覆盖差距（可测试成员 + 当前覆盖）
3. 测试补全计划（按测试类/方法）
4. 实施变更（新增/补全了哪些测试）
5. 验证结果（编译/测试/替代验证）
6. 剩余 TODO / 风险 / 下一步建议
