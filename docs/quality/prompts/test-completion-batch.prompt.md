# 多文件批量补全单元测试总控提示词（Test Completion Batch）

> 版本：v1.0（连续执行版）

使用 $test-project-boundary skill，并严格遵循 AGENTS.md。

任务：针对“指定的一组源码文件”批量补全单元测试（增量方式），按模块/目标测试项目分组执行；不做无关迁移，不修改生产代码逻辑（除非明确授权）。

## 输入参数（执行前填写）
请填写本轮待补测文件清单（示例）：

- `src/Bing.Utils/Bing.Utils.Text/StringHelper.cs` -> `tests/Bing.Utils.Text.Tests/StringHelperTest.cs`
- `src/Bing.Utils/Bing.Utils.Text/MaskHelper.cs` -> `tests/Bing.Utils.Text.Tests/MaskHelperTest.cs`
- `src/Bing.Utils/Bing.Utils.Collections/CollectionExtensions.cs` -> `tests/Bing.Utils.Collections.Tests/CollectionExtensionsTest.cs`

说明：
- 左侧是源码文件
- 右侧是目标测试文件（可不存在，允许创建）
- 目标测试项目由目标测试文件路径推断

测试框架：`xUnit`（如项目已有约定请沿用）  
Mock 框架：按仓库现有约定（如无必要不引入）

## 执行范围
- 允许修改：
  - 本轮指定目标测试文件
  - 必要的测试辅助文件（仅最小范围）
  - `docs/quality/*`（仅当我明确要求记录报告时）
- 不允许修改：
  - `src/*`（生产代码）
  - 本轮清单之外的测试文件

## 本轮处理策略
- 按目标测试项目分组执行（例如 `Bing.Utils.Text.Tests`、`Bing.Utils.Collections.Tests`）
- 若文件数量较多，自动拆分为子批次（如 `TestBatch-1 / TestBatch-2`）
- 优先处理高价值文件（公共工具类、分支复杂、注释约束明确）
- 默认增量补全，不重写已有测试文件

## 任务目标
对每个指定源码文件，补全测试覆盖，优先覆盖：
1. 正常路径（Happy Path）
2. 边界值 / 空值 / 默认值
3. 异常路径（参数校验、非法输入）
4. 关键分支逻辑
5. 回归风险点（依据源码注释 / XML 注释）

> 对纯函数/工具方法优先使用 xUnit `[Theory] + [InlineData]` 进行参数化覆盖。

## 必须遵循的规则
1. 先读取并简要总结：
   - `AGENTS.md`
   - 本轮所有指定源码文件
   - 对应目标测试文件（如存在）
2. 先输出“批量补测计划”（不要直接写代码）
3. 保持测试命名与风格一致（优先沿用各测试项目现有风格）
4. 不猜测行为语义；不确定时基于源码与注释推断，并明确写出依据
5. 不适合单元测试的方法先标记 TODO，不强行编写脆弱测试
6. 不修改生产代码逻辑（`src/*`）

## 执行步骤（按顺序）

### 第1步：批量分析与差距识别（先不改代码）
按“目标测试项目 -> 源码文件”分组输出：
- 可测试成员清单（类/方法）
- 当前测试覆盖情况（如目标测试文件存在）
- 缺失测试清单（高/中/低优先级）
- 风险点（边界、异常、时间、随机、文化区域、线程安全等）

同时输出：
- 本轮是否需要拆分子批次（若总量过大）
- 建议的执行顺序（按价值/风险排序）

### 第2步：批量补测计划（先不改代码）
按“目标测试项目 -> 测试文件 -> 测试方法”输出计划，至少包含：
- 拟新增/补全的测试方法名
- 测试目的
- 输入与预期结果
- 是否参数化测试
- 是否需要最小辅助方法/测试数据构造器

要求：
- 避免重复测试
- 尽量将同类场景合并为参数化测试
- 与现有风格保持一致

### 第3步：执行补全（修改测试代码）
根据第2步计划执行：
- 创建不存在的目标测试文件
- 对已存在测试文件做增量补全（不重写）
- 做最小修复：
  - `using`
  - 命名空间
  - 必要测试引用（仅在确实需要时）
- 不修改生产代码（`src/*`）

### 第4步：最小验证
输出：
- 各目标测试项目编译情况（逐项目列出）
- 本轮目标测试运行情况（如可执行）
- 若无法运行测试，说明原因并提供替代验证（编译检查 / 静态检查 / 结构检查）

同时检查：
- 是否存在重复/冗余测试
- 是否覆盖关键边界与异常路径
- 是否仅修改本轮允许范围

### 第5步：结果总结
请按以下结构输出：
1. 已分析文件与规则摘要
2. 批量覆盖差距与风险点（按项目/文件）
3. 新增/补全测试清单（按项目/文件/方法）
4. 验证结果（编译/测试）
5. 未覆盖项与原因（TODO）
6. 下一步建议（下一子批次 / 混合测试专项 / 参数化扩展）

## 执行策略（连续运行）
- 将本次工作视为一个端到端任务，连续执行直到完成：
  批量分析 -> 批量计划 -> 批量补全 -> 验证 -> 总结
- 不要在每个小步骤后询问“是否继续”
- 若本轮文件数量较多，自动拆分子批次并先完整完成第一个子批次（含验证与总结）
- 仅在以下情况暂停并请求确认：
  1) 需要修改生产代码（`src/*`）
  2) 无法从源码/注释确定行为语义，可能写出错误断言
  3) 需要引入较大测试基础设施重构
  4) 现有测试风格冲突明显，无法安全增量补全

## 输出格式（固定）
请按以下结构输出本次任务结果：
1. 使用规则摘要（已读取哪些文件/规则）
2. 批量分析与覆盖差距（按项目/文件）
3. 批量补测计划（按项目/文件/方法）
4. 实施变更（新增/补全了哪些测试文件/方法）
5. 验证结果（编译/测试/替代验证）
6. 剩余 TODO / 风险 / 下一步建议
