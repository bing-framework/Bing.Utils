# 工具能力收敛性能证据（2026-10-23）

后续 C02 写盘与合并优化已完成独立对照，见 [C02 I/O 报告](c02-io-performance.md)。本文保留该专项之前的原始结果，不覆盖旧基线或原先未收敛的结论。

## 环境与可比边界

- SDK 8.0.425，运行时 .NET 8.0.31；系统 Windows 10.0.22631，种子 20261023。
- 固定基线为实施开始时的真实未提交工作区及 DLL，位于 `artifacts/capability-refinement-2026-10-23/baseline`，不是旧 HEAD。
- 每组预热一次、采样三次，下表列中位数。分配使用 `GC.GetTotalAllocatedBytes(true)` 覆盖进程所有线程，计时不含采样前完整 GC。
- 正式结果是 `before-confirm.json` / `after-confirm.json`。诊断 `before.json` / `after.json` 原样保留；每候选最多一次诊断和一次确认，没有反复选择最好结果。
- 性能运行不与构建/测试并行，正式运行前关闭构建服务器。机器不是专用基准环境，正式耗时与诊断相比变化很大，下表不能解释为稳定吞吐承诺。
- 探针及复现方式见 `benchmarks/CapabilityRefinementProbe/README.md`。显式页大小入口在基线中已存在，正式结果提供可比对照；首次诊断缺少基线页面组，不将它解释为新增 API。

异常调度分别执行 1,000/10,000 次 Task.Yield 后抛 I/O 异常，无磁盘写入；实际峰值并发均达到配置的 1/8/16，调用次数与范围数一致。移除逐片 async 状态后分配量下降。正式确认中调度耗时下降，但首次诊断方向不同，因此只将分配下降作为可重复的资源结论。

成功场景每轮写入 256 个一字节分片。开启检查点时前后均保存 256 次，累计状态文件字节均为 **6,775,424**，没有降低持久化频率。直接流序列化减少约 20 MB 分配；完整快照、刷盘和替换成本仍存在。该场景不能单独区分 JSON 序列化与文件提交耗时，未据此引入新的增量日志格式。

8 MiB 合并改为一次磁盘读取中同时校验并复制，取消摘要预读。正式样本的耗时和分配均高于基线，不能声称合并性能已全面改善；复制路径的缓冲/异步开销仍可后续专项剖析。本轮没有调整摘要强度、文件刷盘或原子提交策略。

显式页面场景使用已预热的共享池，写入同一 8 MiB 内容；测得分配主要是页表及视图，不是全部页面保有量。三种页大小均减少页表分配，但耗时没有统一改善。

## 默认首写与新增流式能力

受控池在 Rent 返回前停止：基线首写请求 **1,024,000,000 B**，候选请求 **65,536 B**。这记录请求容量，不分配旧 GB 级页面，也不将请求值当作进程实际工作集。

| 场景 | Before | 耗时 ms | 分配 B |
|---|---|---:|---:|
| `tabular-v2-stream-1000` | NOT_APPLICABLE | 272.694 | 15,432,160 |
| `tabular-v2-stream-10000` | NOT_APPLICABLE | 540.029 | 153,448,232 |

v2 场景经本地文件逐行写入再读取 1,000/10,000 行（int/string 两列），新接口无历史等价入口。编码和解析仍会为每一行分配 JSON 对象、字符串及独立值数组，总分配随行数增长；一次只保留结构、预读缓冲及当前记录，不能将总分配量等同于峰值保留量。本轮没有测量并声称进程峰值工作集。
