# Bing.Utils 测试项目归属 Skill

## 目的
为 Bing.Utils 多子包 .NET 工具类库仓库应用统一的测试归属规则，确保测试放置位置正确、迁移过程可控、输出结果可审计。

本 Skill 适用于以下场景：
- 将测试从 `Bing.Utils.Tests` 迁移到模块专属测试项目（如 `Bing.Utils.IdUtils.Tests`）
- 审计测试是否放错项目
- 新增测试时判定应放在哪个测试项目
- 拆分“混合测试类”（一个类里同时测多个模块）

- `refs/test-project-boundary.md`

如果存在歧义，先简要总结该文档中的相关规则，再开始执行任务。

## 仓库测试归属规则摘要（Bing.Utils）
- `Bing.Utils.Tests`：用于主包测试、通用/共享测试、真实跨模块测试。
- `Bing.Utils.<Module>.Tests`：用于模块专属测试。
- 示例：所有 `IdUtils` 专属测试必须放在 `Bing.Utils.IdUtils.Tests`。
- 混合测试类优先按“测试方法粒度”拆分（在安全可行时）。
- 不要因为测试“使用了某模块”就迁移；应根据**主要断言目标**判断归属。
- 涉及真实组件协作的测试（如 HTTP 链路）优先放 `*.Integration` 项目（如适用）。

## 使用本 Skill 的执行流程

### A) 测试迁移任务（Migration）
适用示例：
- 将 `Bing.Utils.Tests` 中的 IdUtils 测试迁移到 `Bing.Utils.IdUtils.Tests`

执行步骤：
1. 扫描并分类测试：
   - 可直接迁移
   - 混合测试（需要拆分）
   - 疑似项 / 需人工确认
2. 先输出迁移计划（包含文件路径与迁移依据）
3. 再执行迁移（最小修改原则）：
   - 优先移动文件（move/rename）
   - 修复命名空间、using、项目引用
   - 保持测试语义不变
4. 验证结果：
   - 无重复测试残留
   - 源项目与目标项目可编译
   - 输出待确认项（TODO）

---

### B) 测试归属审计任务（Audit）
适用示例：
- 检查 `Bing.Utils.Tests` 中是否还有放错的 `IdUtils` 测试

执行步骤：
1. 扫描指定测试项目（默认 `Bing.Utils.Tests`）
2. 识别疑似应迁移到模块专属测试项目的测试类/文件
3. 根据归属规则解释原因
4. 仅输出审计报告（除非任务明确要求修改代码）

---

### C) 新增测试归类任务（New Test Placement）
适用示例：
- 为 `Bing.Utils.IdUtils` 新增单元测试并确保放对位置

执行步骤：
1. 判断“主要断言目标”所属模块
2. 按归属规则选择目标测试项目
3. 在正确项目中新增测试
4. 在输出中说明归属依据与未覆盖风险

---

## 约束（必须遵守）
- 优先仅修改测试项目（通常为 `02-tests/*`），除非用户明确允许其他修改。
- 不修改生产代码行为。
- 测试迁移/拆分时必须保持断言语义与测试意图不变。
- 如遇不确定项，标记为 TODO / 待人工确认，不要强行迁移。
- 优先“先计划后执行”，避免误迁移。

---

## 输出格式（固定）
每次执行本 Skill 时，输出应包含以下内容：

1. **使用的规则摘要（简要）**
   - 本次使用了哪些归属规则
   - 是否引用了 `refs/test-project-boundary.md`

2. **分类结果 / 迁移计划**
   - 可直接迁移
   - 混合测试（需拆分）
   - 疑似项（待人工确认）

3. **实施变更（或审计报告）**
   - 修改了哪些文件
   - 做了哪些最小修复（命名空间、using、csproj 引用等）

4. **验证结果**
   - 编译/测试是否通过
   - 是否存在重复测试或引用断裂

5. **剩余 TODO / 风险**
   - 暂未处理项
   - 后续建议（如抽取共享测试辅助类）

---

## 任务执行风格建议
- 先总结规则，再开始改动
- 先输出计划，再执行修改
- 优先小步迁移，减少一次性大改
- 对混合测试类优先按方法拆分，而不是整类复制
